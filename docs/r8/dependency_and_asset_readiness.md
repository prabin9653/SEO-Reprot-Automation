## 3. Transitive closure and lock strategy

* The closure computed from installed metadata (`importlib.metadata`, environment markers evaluated for this machine, extras not
  followed) is **33 packages**: the 13 above plus `certifi, cffi, charset-normalizer, cryptography, googleapis-common-protos, greenlet,
  idna, oauthlib, opentelemetry-api, proto-plus, protobuf, pyasn1, pyasn1-modules, pycparser, pyee, pyparsing, requests-oauthlib,
  typing-extensions, uritemplate, urllib3` (13 + 20 = 33; the lock file is authoritative).
* **Strategy adopted:** a three-layer set of files, all generated by `scripts/dependency_report.py --write-lock` and checked by tests:
  1. `requirements.txt` — direct runtime pins (human-maintained);
  2. `requirements-lock.txt` — the exact 33-package runtime closure;
  3. `requirements-dev.txt` / `requirements-dev-lock.txt` — adds `pytest 9.2.0` and `matplotlib 3.11.2` (the tests take the DejaVu font
     files from matplotlib's data folder; the runner takes them from settings) → 49 packages.
* Install procedure for a reproducible environment (to be performed by a person, **not** done in this stage):

  ```
  py -3.14 -m venv C:\JasperSEO\venv            # OUTSIDE OneDrive and outside the project
  C:\JasperSEO\venv\Scripts\python -m pip install -r requirements-lock.txt
  C:\JasperSEO\venv\Scripts\python -m playwright install chromium
  ```
* **Not done / limits:** the lock has **no hashes** (`pip --require-hashes` would need the wheel hashes from an index, which needs
  network access); no cross-platform lock; the lock records this machine's marker evaluation. Re-generate after any intentional upgrade
  and re-run the suite.

## 4. Playwright and Chromium

* Python Playwright does **not** include a browser. After installing the packages, run once, with network access:
  `python -m playwright install chromium`. It downloads to `%LOCALAPPDATA%\ms-playwright` (or `PLAYWRIGHT_BROWSERS_PATH`). The browser
  revision is fixed by the Playwright version, which is why `playwright` is pinned.
* The renderer launches Chromium headless with no sandbox flags changed, blocks all non-`file:`/`data:` requests, and (R8.4.4) is
  bounded by `execution.stage_timeouts.rendering`.
* **Render reproducibility depends on the browser build.** The sidecar records the Chromium version; if the build changes between a
  render and its retry, the retry is refused as `render_not_reproducible` (a conflict that blocks until an operator decides). Do not
  upgrade Playwright or Chromium in the middle of a reporting month.
* `scripts/check_deployment.py` only checks whether a `chromium-*` folder exists; it does not start the browser.

**Where they are expected.** (Update: the two fonts and `LICENSE_DEJAVU` are now also shipped, unchanged, in `assets/fonts` as the verified source that `seo setup device` copies from into `%LOCALAPPDATA%\JasperSEOReporting\fonts`; a test keeps them identical to matplotlib's copies. The report still reads the fonts only from the locations in `render.fonts`.) `render.fonts` in the runner settings must list both files by
absolute path (see `config/runner.yaml.example`). The tests use the copies inside matplotlib's `mpl-data/fonts/ttf`. For a
deployment, copy the two `.ttf` files and the licence file to a folder outside OneDrive, for example
`C:\JasperSEO\assets\fonts\`, and point the settings at them.

**How fingerprints work.** `asset_fingerprints.sha256_of_file` reads the exact bytes of each file (size-limited, regular files
only, chunked) and `measure_fingerprints` combines the logo hash, the font hashes (by label) and the template version into
`RenderFingerprints`, which become part of the **render input hash**. Consequently **replacing a font or the logo changes every
future render identity**, and a different font file under the same label is refused by the renderer (`fingerprint_mismatch`).
Provision the same files on every machine, and treat a change as a deliberate versioned decision.

**What happens when an asset is missing (verified by tests, today's behaviour).**

| Situation | Where it is detected | Result |
|---|---|---|
| `render.fonts` empty/absent | at the *rendering stage*, after collection | run `failed`, `config_invalid` / `fonts_not_configured` |
| a font or logo file missing/unreadable | at the *rendering stage* | run `failed`, `render_failed` / `render_input_invalid` (the specific cause is only in the sanitized log) |
| settings file invalid (paths, secrets, network DB, ...) | when the settings are loaded, before any run | `RunnerConfigError` with a fixed code and the setting's name |

**Update (R8.6c).** The pipeline itself still finds a missing asset only at the render stage. A **local preflight now exists**: `python -m seo_report doctor`
(section "Fonts and logo") reports a missing/unreadable logo or font, a missing bold face, a file that is not the tested one (a **warning**: every future report identity would change) and
any disagreement between the measured SHA-256 values and the rendering fingerprint implementation (`render_identity.measure_render_fingerprints`), all before any run. The tested reference
hashes above are the constants `preflight.REFERENCE_HASHES`. The check is read-only and never replaces or downloads an asset. `doctor` also checks the dependencies against `requirements.txt`
(missing = blocked, different version = warning), Playwright and the Chromium build folder, and starts headless Chromium once in a separate process to prove it launches
(`--skip-browser-launch` skips this, leaving the check *unverified*). `preflight.production_gate()` will stop `report run|batch` when anything is blocked (wired in R8.6d). The tested
Python is 3.14.x only; any other Python is reported *unverified*, never "compatible". Still *Unverified*: a clean-machine installation.

Before R8.6c, the interim tool was
`scripts/check_deployment.py --settings <runner.yaml>`, which reports `fonts_not_configured`, `file_not_found`, `not_a_regular_file`,
`required_font_file_not_configured` and the file hashes **without** starting a run; run it before every deployment and after every
asset change.

**Provisioning a deployment machine.**
1. Create the folder outside OneDrive (for example `C:\JasperSEO\assets\fonts`).
2. Copy `DejaVuSans.ttf`, `DejaVuSans-Bold.ttf` and `LICENSE_DEJAVU` from a trusted copy of DejaVu Sans 2.35 (for example matplotlib's
   `mpl-data/fonts/ttf`); compare the SHA-256 values above (`Get-FileHash`).
3. Put the absolute paths in `render.fonts` and, if the logo is not the project's, in `render.logo`.
4. Run `scripts/check_deployment.py`. Do not edit the files.
